# Database Connection & CRUD Operations Guide

This guide details the database connection configuration and CRUD (Create, Read, Update, Delete) patterns used in the **java-byod-backend** Spring Boot application. The application connects to a **PostgreSQL** database hosted on Railway and uses Spring's `NamedParameterJdbcTemplate` for type-safe and injection-proof SQL executions.

---

## 1. Database Connection Configuration

The database connection is managed via a custom datasource bean using the **HikariCP** connection pool. It reads PostgreSQL credentials injects at runtime (often from Railway environment variables).

### Configuration Properties
In [application.properties](file:///d:/IdeaProjects/java-byod-backend/src/main/resources/application.properties), the connection configuration points to system environment variables:
```properties
spring.datasource.url=jdbc:postgresql://${PGHOST}:${PGPORT}/${PGDATABASE}
spring.datasource.username=${PGUSER}
spring.datasource.password=${PGPASSWORD}
spring.datasource.driver-class-name=org.postgresql.Driver

# HikariCP connection pool settings
spring.datasource.hikari.maximum-pool-size=5
spring.datasource.hikari.connection-timeout=30000

# Disable Spring Boot auto schema initialization (managed manually via schema.sql)
spring.sql.init.mode=never
```

For local development, these environment variables are supplied in [application-local.properties](file:///d:/IdeaProjects/java-byod-backend/src/main/resources/application-local.properties).

### Custom Data Source Configuration
The [DataSourceConfig.java](file:///d:/IdeaProjects/java-byod-backend/src/main/java/com/pup/byod/javabyodbackend/config/DataSourceConfig.java) class configures the Hikari CP. It explicitly enforces SSL Mode (`sslmode=require`) which is required by Railway PostgreSQL:

```java
package com.pup.byod.javabyodbackend.config;

import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import javax.sql.DataSource;

@Configuration
public class DataSourceConfig {

    @Value("${PGHOST}")
    private String pgHost;

    @Value("${PGPORT}")
    private String pgPort;

    @Value("${PGDATABASE}")
    private String pgDatabase;

    @Value("${PGUSER}")
    private String pgUser;

    @Value("${PGPASSWORD}")
    private String pgPassword;

    @Bean
    public DataSource dataSource() {
        HikariConfig config = new HikariConfig();

        config.setJdbcUrl("jdbc:postgresql://" + pgHost + ":" + pgPort + "/" + pgDatabase);
        config.setUsername(pgUser);
        config.setPassword(pgPassword);
        config.setDriverClassName("org.postgresql.Driver");

        // Connection Pool Settings
        config.setMaximumPoolSize(5);
        config.setMinimumIdle(1);
        config.setConnectionTimeout(30_000); // 30 seconds
        config.setIdleTimeout(600_000);      // 10 minutes
        config.setMaxLifetime(1_800_000);    // 30 minutes

        // Railway PostgreSQL requirement
        config.addDataSourceProperty("sslmode", "require");
        config.setPoolName("byod-hikari-pool");

        return new HikariDataSource(config);
    }
}
```

## 2. Row Mapping Pattern

To map raw JDBC database rows into Java models, the repository layer utilizes Spring's `RowMapper<T>`. This mapping maps columns to fields constructed via Lombok builders.

Example row mapper for the `Student` entity (found in [StudentDAO.java](file:///d:/IdeaProjects/java-byod-backend/src/main/java/com/pup/byod/javabyodbackend/dao/StudentDAO.java)):

```java
private final RowMapper<Student> studentRowMapper = (rs, rowNum) -> Student.builder()
        .studentId(rs.getString("student_id"))
        .firstName(rs.getString("first_name"))
        .lastName(rs.getString("last_name"))
        .courseYearLevel(rs.getString("course_year_level"))
        .status(rs.getString("status"))
        .createdAt(rs.getTimestamp("created_at") != null
                ? rs.getTimestamp("created_at").toLocalDateTime() : null)
        .updatedAt(rs.getTimestamp("updated_at") != null
                ? rs.getTimestamp("updated_at").toLocalDateTime() : null)
        .build();
```

## 3. CRUD Operations

### A. Create (Insert)

Depending on whether primary keys are client-provided or auto-generated by the database, there are two distinct creation patterns.

#### Pattern 1: Client-provided Keys (e.g., student ID)
For tables like `students` where the key is generated externally or entered manually, a simple `jdbc.update(...)` execution is used:

```java
public int insert(Student student) {
    String sql = """
            INSERT INTO students (student_id, first_name, last_name, course_year_level, status)
            VALUES (:studentId, :firstName, :lastName, :courseYearLevel, :status)
            """;

    var params = new MapSqlParameterSource()
            .addValue("studentId", student.getStudentId())
            .addValue("firstName", student.getFirstName())
            .addValue("lastName", student.getLastName())
            .addValue("courseYearLevel", student.getCourseYearLevel())
            .addValue("status", student.getStatus());

    return jdbc.update(sql, params);
}
```

#### Pattern 2: Database-generated Keys (e.g., serial primary keys)
For entities like `User` or `Device` where `user_id` or `device_id` is an auto-incrementing serial primary key, the generated key is captured using a `KeyHolder`:

```java
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

public int insert(User user) {
    String sql = """
            INSERT INTO users (username, email, password_hash, full_name, role, status)
            VALUES (:username, :email, :passwordHash, :fullName, :role, :status)
            """;

    var params = new MapSqlParameterSource()
            .addValue("username", user.getUsername())
            .addValue("email", user.getEmail())
            .addValue("passwordHash", user.getPasswordHash())
            .addValue("fullName", user.getFullName())
            .addValue("role", user.getRole().name())
            .addValue("status", user.getStatus());

    KeyHolder keyHolder = new GeneratedKeyHolder();
    jdbc.update(sql, params, keyHolder, new String[]{"user_id"});
    
    // Return the generated primary key
    return keyHolder.getKey().intValue();
}
```

### B. Read (Select)

Retrieving records uses standard SQL queries combined with the `RowMapper`.

#### Pattern 1: Fetch List (Find All or Search)
Returns a list of records.

```java
public List<Student> findAll() {
    String sql = "SELECT * FROM students ORDER BY last_name, first_name";
    return jdbc.query(sql, studentRowMapper);
}

// Case-insensitive search using SQL LIKE
public List<Student> search(String keyword) {
    String sql = """
            SELECT * FROM students
            WHERE lower(student_id) LIKE lower(:kw)
               OR lower(first_name) LIKE lower(:kw)
               OR lower(last_name)  LIKE lower(:kw)
            ORDER BY last_name, first_name
            """;
    var params = new MapSqlParameterSource("kw", "%" + keyword + "%");
    return jdbc.query(sql, params, studentRowMapper);
}
```

#### Pattern 2: Fetch Single Record (Find by Identifier)
Returns an `Optional<T>` containing either the matched record or empty.

```java
public Optional<Student> findById(String studentId) {
    String sql = "SELECT * FROM students WHERE student_id = :studentId";
    var params = new MapSqlParameterSource("studentId", studentId);
    
    // Querying and returning the first element or empty using Java Streams
    return jdbc.query(sql, params, studentRowMapper).stream().findFirst();
}
```

### C. Update

Updating changes parameters in specific rows based on identifier parameters.

#### Pattern 1: Full / Model-level Update
Replaces the values of all mutable columns for the matched identifier:

```java
public int update(Student student) {
    String sql = """
            UPDATE students
            SET first_name       = :firstName,
                last_name        = :lastName,
                course_year_level = :courseYearLevel,
                status           = :status
            WHERE student_id = :studentId
            """;

    var params = new MapSqlParameterSource()
            .addValue("firstName", student.getFirstName())
            .addValue("lastName", student.getLastName())
            .addValue("courseYearLevel", student.getCourseYearLevel())
            .addValue("status", student.getStatus())
            .addValue("studentId", student.getStudentId());

    return jdbc.update(sql, params);
}
```

#### Pattern 2: Single Column / Status Update
Updates specific fields directly (e.g. status flag):

```java
public int setStatus(String studentId, String status) {
    String sql = "UPDATE students SET status = :status WHERE student_id = :studentId";
    var params = new MapSqlParameterSource()
            .addValue("status", status)
            .addValue("studentId", studentId);
            
    return jdbc.update(sql, params);
}
```

### D. Delete (and Deletion Protection)

#### Hard Deletes vs. Deletion Protection
The BYOD Backend prevents direct deletions of core records (e.g., users, students, and devices) to keep an audit trail intact. The PostgreSQL schema enforces this through triggers:
1. **Students**: Protected from deletion if they have registered devices or gate log entries ([schema.sql:L657-681](file:///d:/IdeaProjects/java-byod-backend/src/main/resources/db/schema.sql#L657-L681)).
2. **Devices**: Protected if they have gate log history ([schema.sql:L684-706](file:///d:/IdeaProjects/java-byod-backend/src/main/resources/db/schema.sql#L684-L706)).
3. **Users**: Protected if they have audit logs ([schema.sql:L709-731](file:///d:/IdeaProjects/java-byod-backend/src/main/resources/db/schema.sql#L709-L731)).

Therefore, the core models use **Soft Deletes** by updating status values (e.g., `status = 'inactive'`).

#### Standard Soft Delete (Deactivation Pattern)
```java
public int deactivateStudent(String studentId) {
    String sql = "UPDATE students SET status = 'inactive' WHERE student_id = :studentId";
    var params = new MapSqlParameterSource("studentId", studentId);
    return jdbc.update(sql, params);
}
```

#### Standard Hard Delete (For Transient/Cascading Tables)
If hard deleting temporary records (such as a temporary device registered under an event request, or clearing password tokens), execute:
```java
public int deleteEventDevice(int eventDeviceId) {
    String sql = "DELETE FROM event_request_devices WHERE event_device_id = :eventDeviceId";
    var params = new MapSqlParameterSource("eventDeviceId", eventDeviceId);
    return jdbc.update(sql, params);
}
```

## 4. Input Validation & Data Integrity

Data inputs are validated programmatically at the service and controller boundary layers using [ValidationUtil.java](file:///d:/IdeaProjects/java-byod-backend/src/main/java/com/pup/byod/javabyodbackend/util/ValidationUtil.java) before any CRUD database calls are executed. This keeps the database consistent and avoids exposing raw database constraint error messages.

### A. Central Validation Helpers
* **Name Validation (`requireValidName`)**: Rejects any name string containing numeric digits or characters other than letters, spaces, hyphens, periods, and apostrophes.
* **Email Validation (`requireValidEmail`)**: Enforces standard email formatting rules via regular expression.
* **Username Validation (`requireValidUsername`)**: Enforces username restrictions (3-100 characters, alphanumeric, dots, hyphens, underscores, and `@`).
* **Serial Number Validation (`requireValidSerialNumber`)**: Enforces serial number formatting (no whitespaces, maximum 100 characters).

### B. Business-Level Checks
* **Date Restrictions**:
  * Event request start and end dates must be in the present or future (on or after `LocalDate.now()`).
  * End date must not fall before the start date.
* **System Setting Constraints**:
  * `max_devices_per_student`: Validated as an integer between 1 and 20.
  * `allow_unregistered_devices`: Must be exactly `"true"` or `"false"` (case-insensitive).
  * `event_request_max_duration_days`: Validated as an integer between 1 and 30.
* **Event Device Line Items**:
  * Quantities must be greater than zero.
  * Device category is validated against database-allowed enum values prior to DB execution.

### C. Validation Code Snippets

#### 1. Central Helper Methods (`ValidationUtil.java`)
```java
// Central validator helper method rejecting numbers/illegal symbols in names
public static void requireValidName(String name, String fieldName) {
    requireNonBlank(name, fieldName);
    if (!name.matches("^[\\\\p{L}\\\\s\\\\-\\\\.\\\\']+$")) {
        throw new BusinessRuleException(fieldName + " must contain only letters and name-appropriate symbols (spaces, hyphens, periods, apostrophes).");
    }
}

// Central validator checking email format regex
public static void requireValidEmail(String email) {
    requireNonBlank(email, "Email");
    if (!email.matches("^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\\\.[A-Za-z]{2,}$")) {
        throw new BusinessRuleException("Email format is invalid.");
    }
}
```

#### 2. Service/Controller Level Usage (`StudentController.java`)
```java
@PostMapping
public ResponseEntity<Student> createStudent(@RequestBody CreateStudentRequest request) {
    ValidationUtil.requireValidStudentId(request.studentId);
```

## 5. Best Practices for Database Operations

1. **Avoid SQL Injection**: Always use named parameters (`:paramName`) with `MapSqlParameterSource`. Do not concatenate strings inside SQL statements.
2. **Use Multi-line SQL text blocks**: Utilize Java's triple double-quotes (`"""`) for cleaner formatting and readability of complex query logic.
3. **Handle Optional Returns**: Always return `Optional<T>` for queries that target a single record by unique keys, so caller functions can safely utilize `.orElseThrow()` or `.map()`.
4. **Use Postgres Timestamps**: Java timestamps mapped to Postgre's `TIMESTAMPTZ` should be converted correctly (e.g., using `rs.getTimestamp(column).toLocalDateTime()` or mapping `OffsetDateTime`).
